# P2-4 — Route parameters are not URL-decoded: `locate("/users/42%20x")` yields …

## Finding / 问题

- EN: Route parameters are not URL-decoded: `locate("/users/42%20x")` yields the literal `42%20x` while `$_GET` would decode it, so one request carries two semantics. (The side effect is that `%2e%2e` traversal is also unusable, which is a security plus.)
- 中文: 路由参数不做 URL 解码：locate("/users/42%20x") 得到字面量 42%20x，而 $_GET 会解码，同一个请求两套语义。（副作用是 %2e%2e 型穿越也因此不可用，安全上是加分。）
- Where / 位置: `src/Request.php:53, src/ResourceLocator.php:59`
- Verification / 验证: reproduced / 已实证

- 2026-09-28 · `owner — migears-web` · `deferred` — **deferred, with a reason.** The reviewer is factually right: `locate("/users/42%20x")` yields the literal `42%20x` while `$_GET` decodes, so one request carries two semantics. This is deliberate, not accidental, and is now documented and pinned: the README paragraph "Route parameters keep their raw URL encoding" states that `___param___` values are passed through as-is, that `urldecode()` is the caller's job, and that keeping the raw encoding denies path-traversal variants such as `%2e%2e` a decoded form — the security plus the finding itself notes. `MiRestTest::testRouteParametersKeepTheirRawUrlEncoding` pins the behaviour. It will not change without a decision to trade that protection for decoded-by-default parameters.
